# JARVIS Proposal：会找东西、记得东西放哪的桌面助手

> 组号：__ ｜ 成员：__（单人） ｜ 提交日期：2026-11-02

## 1. 一句话概述

一个装在 SO101 机械臂上的桌面助手。你问它“我的钥匙呢？”“把那支红笔指给我看”，它会**主动转动腕部相机扫视桌面**，从多个视角**估计物体的三维位置**，然后**用手指向、触碰或抓起**这个物体；它还会**记住**桌上各个物品最后一次出现的位置，下次直接回答“在你左手边的书旁边”，并转过去确认。

## 2. 想实现的功能（分层交付）

| 层级 | 功能 | 体现的闭环 |
|---|---|---|
| **保底** | 语音对话；按口头描述找到并持续追踪目标（目标保持在画面中央）；用末端指向目标 | 语音 → VLM 识别 → 视觉伺服追踪 → 指向 |
| **目标** | 主动扫视 + 多视角定位，得到物体在机械臂坐标系下的 3D 位置；规划并执行**触碰**，最后几厘米用视觉反馈修正；对轻小物体尝试**抓取** | 感知 → 主动改变视角 → 3D 估计 → 规划 → 执行 → 视觉校正 |
| **冲刺** | **空间记忆**：维护“物品 → 位置、时间、置信度”的记忆，回答“东西放哪了”；发现物品被挪走时更新记忆；支持“你刚才看到我的杯子了吗” | 长时记忆 + 主动验证 |

每一层都能独立演示，前一层是后一层的基础，所以即使冲刺目标没完成，Demo Day 也有完整可展示的系统。

## 3. 为什么有意思

- **有用**：找东西是日常里真实而高频的需求，“东西放哪了”比“帮我捡个球”更接近一个助手该做的事。
- **它不得不主动感知**：只有腕部相机（eye-in-hand），没有固定的全局视角。机器人要看清楚，就必须**移动自己的身体去看**。看和动在这里是同一件事，这正是具身智能的核心：感知取决于动作，动作又依赖感知。
- **单目没有深度**：单张图得不到距离，只能靠移动相机制造视差，或借助桌面平面这类先验。“如何选视角、看几次才够”本身就是一个值得做实验的问题。
- **低精度硬件下的精细动作**：SCS215 舵机是 10 位编码器（约 0.32°/步），额定扭矩约 6 kg·cm，存在回差和柔顺性。开环往往碰不准，所以我想研究**闭环视觉修正能把成功率提升多少**。
- **记忆让它从“反应式”变成“有历史的”**：机器人需要区分“我现在看到的”和“我记得的”，并处理记忆过期的问题。

## 4. 大致实现思路

### 4.0 已有基础

前期已经有一套 SO101 + SCS215 控制工具（本仓库），验证过以下环节：SCSCL 驱动与 EEPROM 限位、六轴状态监视、基于 URDF 的 IK 笛卡尔直线运动、相机内参与手眼标定（`T_gripper_camera`）、ArUco 简单视觉伺服真机闭环、四角点 IBVS 仿真，以及本地中文语音识别（sherpa-onnx）加白名单指令。这些代码是按模块分别写的脚本，没有统一的接口，所以本项目会把它们重构成统一的 HAL 和 Agent 框架。新增的部分主要是：开放词汇的物体识别（不再依赖 ArUco）、LLM 工具调用、主动扫视与多视角定位、触碰/抓取策略和空间记忆。

### 4.1 系统框架

```
 麦克风 ─► ASR(API) ─► 对话 Agent(LLM + function calling) ─► TTS(API) ─► 扬声器
                              │ 调用工具
         ┌────────────────────┼─────────────────────┐
         ▼                    ▼                     ▼
   视觉 Agent             空间记忆               动作 Agent
 VLM 语义定位(API)     物品→位置/时间/置信度    FK/IK、扫视轨迹、
 本地快速追踪(OpenCV)                          指向/触碰/抓取、视觉伺服
         └──────────── 硬件抽象层(HAL) ──────────────┘
                 机械臂(SCSCL 驱动) / 腕部相机
                 真机实现 ←→ 录制回放实现
```

对话 Agent 不直接控制电机，只调用一组高层工具，例如 `scan()`、`find(name)`、`track(name)`、`point(name)`、`touch(name)`、`grasp(name)`、`where_is(name)`。这样 LLM 的不确定性被限制在“决定做什么”，“怎么做”由确定性的代码负责，更安全，也更容易调试。

### 4.2 关键技术点

1. **驱动与 HAL**：LeRobot 自带的驱动面向 STS 系列，不能直接用，所以基于 SCSCL 协议自己写驱动（读写位置、速度、扭矩开关）。HAL 提供真机和回放两套实现，回放实现可以在云端离线测试算法。
2. **运动学与标定**：用 SO101 的 URDF 做正/逆运动学；关节零点标定；用棋盘格或 ArUco 做手眼标定，求相机到末端的变换。
3. **识别：慢模型 + 快模型**：VLM（API，约 1–3 s）负责“哪个是我的钥匙”这类语义定位，给出初始框；本地轻量追踪器（OpenCV 追踪 / 颜色 / 模板）以 15–30 FPS 跟住目标，用于视觉伺服。
4. **3D 定位**，打算对比两种方法：
   - **射线–桌面求交**：已知桌面平面后，一个视角就能得到位置，简单但依赖平面假设；
   - **多视角三角化**：从 N 个位姿观察，把各条射线在基座坐标系下做最小二乘求交，不依赖平面，但对标定误差更敏感。
5. **主动扫视**：先按预设的“扫视姿态序列”覆盖桌面；找到候选后，围绕目标选择基线足够大的新视角补拍，用于三角化。
6. **触碰 / 抓取**：先用 IK 移到目标上方的预备点（开环），再在最后一段用腕部相机做视觉伺服，让目标对准画面中预先标定的“指尖位置”，慢速下压，靠电流或位置误差检测接触。抓取只针对轻、大（> 3 cm）、形状规则的物体，自上而下夹取。
7. **空间记忆**：每次看到物体就更新它的位置、时间戳和置信度；回答时先查记忆，再转过去确认。如果在记忆位置没看到物体，就降低置信度并重新扫视。

### 4.3 工程与安全

- 软件关节限位、限速、限扭矩；键盘急停（一键卸力）；指令越界直接拒绝执行。
- 每次运行自动记录日志：关节指令与反馈、相机帧（抽样）、VLM 请求与返回、对话记录，可以离线回放复现。
- 本地配置（COM 口、标定结果、API key）不进仓库；代码放在 GitHub，云端开发和离线测试，本地拉取后上机运行。

## 5. 计划做的实验（探索与发现）

| 问题 | 实验 |
|---|---|
| 舵机精度到底限制在哪里？ | 测量各关节回差、重复定位误差，以及负载下末端的下垂量 |
| 用几个视角、多大的基线才够？ | 用已知位置的标记物，比较“单视角 + 桌面”和 N 视角三角化的定位误差 |
| 闭环修正值多少？ | 同一组目标分别做开环和视觉伺服触碰，比较成功率和误差 |
| 慢 VLM 和快追踪器怎么配合？ | 测量端到端延迟，分析“VLM 认错”和“追踪丢失”各占多少失败 |
| 记忆什么时候会骗人？ | 人为移动物品，统计记忆过期带来的错误，以及主动确认能挽回多少 |

成功和失败的案例都会记录，作为 Checkpoint 和 Demo Day 的证据。

## 6. Demo Day 计划展示

**理想流程（约 3 分钟）**

1. 桌上随意摆 5–6 件日常物品（钥匙、红笔、杯子、橡皮等）。
2. “JARVIS，看看桌上有什么。”它扫视一圈，口头报出物品，同时建立记忆。
3. “红笔在哪？”它转过去，追踪并指向红笔。观众可以拿着红笔移动，它会一直跟着。
4. “碰一下杯子。”它主动换一个视角定位，移动过去轻触杯子。
5. “把橡皮拿起来。”尝试抓取。
6. 我当着观众的面把钥匙藏到书后面，再问“我的钥匙呢？”。它先去记忆中的位置看，发现不在，说明情况后重新扫视找到钥匙。

**同时展示**：系统工作方式和关键设计选择、实验数据（定位误差、开环与闭环对比）、典型失败案例和原因。

**备选方案**：现场光线或网络出问题时，退到保底层（追踪 + 指向），并准备完整流程的录屏。

## 8. 主要风险与应对

| 风险 | 应对 |
|---|---|
| 舵机精度或扭矩不足，抓不住 | 抓取只作为目标层的加分项；触碰依靠视觉伺服；挑选轻、大的物体 |
| 手眼标定误差导致定位不准 | 最后一段用视觉伺服兜底；用实验量化误差来源 |
| VLM 延迟或认错 | VLM 只负责初始定位，追踪交给本地；对低置信度结果反问用户 |
| 现场网络不稳定 | 语音识别退回已有的本地 ASR；识别退回颜色或 ArUco 标签；准备录屏 |
| 单人工作量 | 严格分层，先保证保底层端到端可用，再往上做 |

## 9. 其他考虑过的方向

- **社交 / 共同注意机器人**（看着说话的人、顺着手指的方向看过去）：交互上很有意思，但不容易定义“完成度”。其中“顺着手指找物体”可以作为本项目的扩展，比如“那个东西是什么？”
- **桌面游戏对手**：规则明确，但对“主动感知”的要求较弱。
- **读屏幕、代回消息**：受舵机精度限制，敲键盘的风险太高，暂不采用。
